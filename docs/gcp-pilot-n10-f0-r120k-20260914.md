# GCP 10-Node No-Fault Pilot (2026-09-14)

## Purpose

This pilot reruns the same 10-node, 120k tx/s WAN point as the preceding one-silent-node pilot, but with all ten nodes active. It checks the no-fault fast paths and compares the current implementation with archived paper data.

## Configuration

- GCP project: `shortfin`
- Protocol code commit deployed on the VMs: `3fa44f8a62997a4ef95d2132518d12ad9b221d8b`
- Topology: 10 nodes in 5 zones, 2 `n2-standard-2` VMs per zone
- Zones: `europe-west1-b`, `us-west1-a`, `asia-east1-a`, `us-east1-b`, `asia-southeast1-a`
- Faults: 0
- Workers: 1 per node; primary and worker collocated
- Input rate: 120,000 tx/s; transaction size: 512 B
- Requested duration: 50 s; mesh warm-up: 20 s
- Header size: 1,000 B; maximum header delay: 1,000 ms
- Batch size: 500,000 B; maximum batch delay: 200 ms
- GC depth: 50 rounds; sync retry delay: 10,000 ms; sync retry nodes: 3
- Consensus protocol setting: `round_robin`

The existing VM disks and compiled remote binaries were reused. Each invocation still regenerated keys and configuration, uploaded them to ten machines, waited for ports and mesh warm-up, and downloaded 30 logs.

## Archived Paper Comparison

The archived paper files contain the same nominal no-fault configuration for Narwhal, the old `noveldag` Shortfin, and Wahoo.

| Protocol | Current consensus TPS / latency | Archived consensus TPS / latency | TPS delta | Latency delta |
|---|---:|---:|---:|---:|
| Narwhal/Tusk | 98,564 / 5,417 ms | 86,573 / 5,845 ms | +13.85% | -7.32% |
| Shortfin | 115,126 / 4,723 ms | 114,612 / 4,090 ms | +0.45% | +15.48% |
| Wahoo | 112,470 / 1,866 ms | 115,172 / 2,490 ms | -2.35% | -25.06% |

The archived no-fault files report consensus and end-to-end metrics as exactly identical for all three protocols. Current parsing includes an additional worker/client delay, so consensus metrics are the cleaner historical comparison. In that view, Shortfin and Wahoo throughput are close to the old data. Narwhal's +13.85% is a larger but still plausible single-run WAN variation; its current result also closely matches the recent 93,316 E2E TPS cloud scratch run.

Mahi-Mahi has no archived paper baseline. Compared with the immediately preceding one-silent-node pilot, no-fault E2E throughput is nearly unchanged (107,629 versus 107,333 tx/s) while latency falls by about 13.2% (4,933 versus 5,682 ms), which is directionally reasonable.

## Log Findings

### Narwhal/Tusk

- All ten primaries committed throughout the measurement window.
- Eight primaries reached committed round 74 and two reached round 72 at shutdown, a small normal catch-up difference.
- No liveness anomaly was found.

### Shortfin

- The protocol did not reproduce the global round-57 stall from the one-silent-node run.
- Seven primaries committed through round 75. Three stopped committing at round 63, although their proposers continued to rounds 69 or 74.
- This is uneven end-of-run decision catch-up rather than a global protocol stop. The throughput point is usable as a pilot, but the cross-node lag should be checked before publication runs.

### Mahi-Mahi-5

- All ten primaries committed through rounds 97-98.
- The result covers the complete window and shows no protocol-progress anomaly.

### Wahoo

- Wahoo initially followed its fast path and all ten primaries committed 4,301 records through round 99.
- The final commit occurred around 14 seconds before process shutdown.
- All ten primaries then stopped at round 101 with `move_count=6/7`.
- This has the same missing-progress shape as the one-silent-node run, which stopped at round 5 with `6/7`, but the no-fault fast path advances much farther before encountering it.
- TPS is calculated over the 39-second active commit interval and should not be used as a sustained 50-second paper result.

Connection-refused warnings clustered at process startup and coordinated shutdown, when peers came up or were killed at slightly different times. They are not evidence of mid-run VM failure.

## Interpretation

1. The cloud environment and workload path remain healthy: three protocols produced complete-window results, and current throughput is in the same broad range as archived data.
2. Shortfin is live without faults and matches archived consensus throughput closely, but several replicas lag in final decisions.
3. Wahoo's low fast-path latency is plausible, but its late `6/7` stall confirms that the current WAN liveness issue is not limited to a Byzantine or silence path.
4. No protocol code was changed or repaired during this run.
