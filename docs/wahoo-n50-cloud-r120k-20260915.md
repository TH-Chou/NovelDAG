# Wahoo 50-node cloud probe, 2026-09-15

Goal:
- Test whether the repaired Wahoo implementation can run on the 50-node GCP
  WAN testbed at the existing 120k offered-load point.

Setup:
- GCP project: `shortfin`
- Commit: `9a4e7f79de1487412c775aa43b48b0b1f004f071`
- Nodes: 50 replicas, 5 regions, 10 VMs per region
- Machine type: `n2-standard-2`
- Disk: 25GB `pd-ssd`
- Protocol: `wahoo`
- Faults: 0
- Workers: 1 per node
- Input rate: 120,000 tx/s, 512B transactions
- Benchmark duration: 40 seconds, with 20 seconds mesh warm-up
- Consensus leader schedule: round robin

Infrastructure notes:
- The testbed had previously been shrunk to 10 stopped VMs. I expanded it back
  to 50 VMs.
- `fab create --nodes=10` counts only active instances for GCP and tried to
  create too many VMs when old instances were stopped. It reached the
  `SSD_TOTAL_GB=250GB` quota in `asia-east1` after creating the eight actually
  needed additional VMs there. The remaining regions were filled manually.
- `europe-west1-b` had no available `n2-standard-2` capacity, so the eight new
  Europe VMs were created in `europe-west1-d`, matching the two existing Europe
  VMs. The regional layout is still 10 VMs per configured region.
- The recurring bad external IP `34.143.249.27` was assigned again. The
  affected VM was replaced and came back as `34.126.177.185`.
- All 50 VMs were verified running before the experiment and then verified
  `TERMINATED` after the run.

Result:

| Metric | Value |
| --- | ---: |
| Consensus TPS | 4,902 tx/s |
| Consensus latency | 33,080 ms |
| End-to-end TPS | 4,330 tx/s |
| End-to-end latency | 35,930 ms |
| Config hash verified | yes |

Diagnosis:
- This is not a zero-throughput stall: logs were collected from all 50 nodes,
  the distributed config hashes matched, and most primaries did commit.
- It is still not a valid performance point. Wahoo only advanced to very low
  rounds during the 40-second run. The primary logs show EPBC/PBC activity only
  up to roughly rounds 8-9, and committed records only for rounds 6-7.
- Five primary logs had no local commit records; the others had exactly 358
  commit records. There were no panic/fatal errors, and clients did not report
  missed target warnings.
- EPBC phase counts show heavy slow-path activity even without Byzantine
  faults: about 11,049 `Ts1` certificates, 10,358 `Ts2` certificates, and
  9,478 `Tf` certificates. Deliveries were mostly `Ts2`, not just fast-path
  `Tf`.
- Logs also contain thousands of transient `Connection refused` and
  `unexpected ACK` warnings while nodes were establishing and recycling
  connections. These warnings do not explain a crash, but they are consistent
  with Wahoo's much heavier all-to-all EPBC/PBC message pattern overwhelming
  this 50-node deployment.

Conclusion:
- The 10-node Wahoo liveness fix is still useful: the protocol no longer
  trivially stalls at zero throughput.
- At 50 nodes, Wahoo remains effectively unusable at 120k offered load in this
  implementation. The observed bottleneck is protocol progression under the
  50-node message load, not client input or a single failed VM.
- Do not include this point in the paper curve as a valid Wahoo datapoint. Use
  it as a diagnostic failure point unless Wahoo is further optimized or tested
  at much lower rates.
